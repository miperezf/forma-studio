# Decisiones de arquitectura (ADR) — reversibles, tomadas sin consulta según el prompt de finalización

| ADR | Decisión | Motivo | Cómo revertir |
|---|---|---|---|
| 0001 | Staging = sitio estático de archivo único (`dist/staging/index.html`) en Firebase Hosting | La Beta no tiene build; un archivo es reproducible y verificable | Servir `apps/beta-web` modular |
| 0002 | `firebase.json` **generado** por `scripts/build-staging.mjs` con CSP por hashes | Los hashes deben coincidir con el bundle; evita `unsafe-inline` | Mantener a mano con `unsafe-inline` (peor) |
| 0003 | React+Vite se introduce **después** de Gate F/A, migrando por pantallas y reutilizando `styles.css` (revisada por ADR-0010) | Conservar UX aprobada | Mantener JS plano |
| 0004 | Dependencias fijadas por línea mayor (zod ^3.25, esbuild ^0.28, eslint ^10, typescript-eslint ^8.65, vitest ^4, fast-check ^4, tsd ^0.33, dependency-cruiser ^17, firebase-tools 15) | Evitar `latest` (zod 4 rompe la API usada) | Ajustar al primer `npm install` con registro; fijar lockfile |
| 0005 | Idempotencia de «aceptar + pedido»: documento `orderLocks/{quoteId}` creado en la misma transacción que el pedido; folio `PED-n` = max(contador, máximo local)+1 y aborta si ya existe; reglas exigen el candado (sin Cloud Functions) | Funciona en plan gratuito; garantiza 1 pedido por cotización aunque haya 2 dispositivos | Callable function si se requiere lógica de servidor |
| 0006 | Confirmación de acciones destructivas dentro de la página (`askConfirm`) | `window.confirm` bloqueado en algunos visores y fuera del diseño | Volver a `window.confirm` |
| 0007 | Variante de build `preview` para claude.ai (sin envoltura html, impresión deshabilitada con aviso) | Visor de claude.ai bloquea `print()` y `confirm()` | Eliminar la variante cuando exista staging Firebase |
| 0008 | Régimen tributario explícito en la configuración (`taxRegime`) | Prompt D2: no deducirlo de la tasa | — (requisito) |
| 0009 | Firebase JS SDK **^12.19** + `@firebase/rules-unit-testing` ^5 (no SDK 13) | SDK 13.0.0 salió el 2026-10-07; rules-unit-testing 5 declara peer firebase ^12 | Subir a 13 cuando rules-unit-testing lo soporte |
| 0010 | El modo nube se integra en la Beta actual (JS plano) mediante un bundle IIFE `FormaFirebase` generado desde `src/infrastructure/firebase`; la UI no importa `firebase/*` | Entregar Gate F/A sin reescribir la UI aprobada; R11 mantiene Firebase aislado | Reemplazar el bundle por imports directos al migrar a React |
| 0011 | Acceso solo propietario: Google Auth + lista de correos verificados inyectada en las reglas al construir (`.env.local` → `firestore.rules`, no versionado) | Sin contraseñas que custodiar; sin Admin SDK en el frontend | Custom claims vía Admin SDK local si hay más usuarios |
| 0012 | Pagos idempotentes por `paymentId` generado en la UI; reglas: lista de pagos solo crece (append-only) | Doble clic o reintento no duplica pagos | Subcolección `payments/{paymentId}` |
| 0013 | Respaldo **manual** descargable (JSON) y restauración que solo agrega (nunca sobrescribe/elimina) en vez de exportación programada de Firestore | Decisión del propietario: sin plan Blaze ni costos; restaurar no destructivo evita migraciones destructivas | Exportación programada (`gcloud firestore export`) al pasar a Blaze |
| 0014 | Producción en proyecto Firebase **separado** (`forma-studio-prd-*`), creado por `CREAR_PRODUCCION.cmd` con confirmación escrita | Aislar datos reales de staging | — |
| 0015 | Catálogo de filamentos como **instantánea versionada** generada desde Open Filament Database (10 marcas, 1,75 mm), embebida en la app; no se consulta la API en tiempo de ejecución | Sin dependencia de red ni ampliar la CSP; resultados reproducibles; ~270 KB | Cargar `filament-catalog.json` bajo demanda desde Hosting si crece |
| 0016 | Multicolor como filamentos adicionales de la MISMA placa (`extraFilaments`, opcional en `formState`) usando el soporte nativo del motor (`plate.filaments[]`) | Sin cambiar el motor ni romper snapshots antiguos | Varias placas por cotización si se necesita |
| 0017 | ~~Consumo automático al pasar a «En producción»~~ — **reemplazada por ADR-0019** (nunca publicada) | — | — |
| 0018 | Motor `calculation/v2`: última placa incompleta con datos propios (`PlateSpec.lastRun`) calculada reutilizando los generadores v1 sobre una placa virtual `<id>.last`; sin datos = estimación conservadora (= v1) con flag | Precisión sin duplicar fórmulas ni romper v1; equivalencia demostrable | Proporcionalidad configurable si el propietario la aprueba |
| 0019 | Inventario: la cotización solo estima; el stock se mueve con consumos REALES registrados (append-only, id único, transacción pedido+materiales) | Requisito del propietario: diferenciar estimado vs efectivo, reimpresiones y desperdicio | — |
| 0020 | Inventario con **reservas**: el pedido compromete la estimación (no toca el físico); el consumo real de producción descuenta el físico y libera la reserva; disponible = físico − comprometido (calculado, no guardado) | Visibilidad desde la aceptación sin mezclar estimado y real; stock físico auditable con balanza; reservas trazables | Descontar al aceptar (descartado: físico deja de ser confiable) |
| 0021 | Pedidos: **corrección** = volver UN estado atrás con motivo y evento `PRODUCTION_REVERTED`; **anulación** = estado terminal `Anulado` con `cancelled {at, reason, fromStatus}` que libera la reserva, deja de contar y bloquea abonos. Nunca se borra; historial append-only en reglas | El propietario necesita deshacer errores sin perder trazabilidad; borrar pedidos rompería folios, abonos, consumos y auditoría | Alternativas: borrar (rechazada: pierde historial y no lo permiten las reglas) o editar el estado libremente (rechazada: sin auditoría). Anular no se revierte; para rehacer se crea una revisión de la cotización |
| 0022 | Importación de Bambu Studio **en el navegador**: lector ZIP propio con `DecompressionStream` que lee solo `slice_info.config`, `project_settings.config` y el título; varias placas como `extraPlates` del formulario (placa n: unidades por placa → `partsPerPlate`, `partsPerUnit = 1`), sin cambiar el motor | Sin red ni librerías externas (CSP estricta); los datos del cliente no salen del equipo; el motor ya admitía varias placas | Alternativas: subir el archivo a un servidor (rechazada: costo, privacidad y plan Spark) o librería ZIP de terceros (innecesaria). La última placa con datos propios sigue disponible solo en la placa 1; en las demás, un resto se estima como placa completa con aviso |
| 0023 | Productos frecuentes como colección propia `products` (plantilla = `formState` sin cliente ni precio); historial de material **derivado** de pedidos (reservas y consumos) más un `stockLog` corto en el material para ajustes manuales; resultado real vs. cotizado calculado al vuelo desde el snapshot | Reutilizar cómo se fabrica sin congelar precios; no duplicar datos que ya existen (consumos y reservas son la fuente) | Alternativa: colección de movimientos de inventario (rechazada por ahora: duplicaría consumos y exigiría transacciones extra; se revisará si hay compras de filamento con proveedor) |
